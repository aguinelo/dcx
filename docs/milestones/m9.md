# M9 — Conversa e app desktop

## Objetivo

Separar conversa de execução para permitir explorar um projeto, discutir arquitetura e só depois iniciar um run com contrato e sensores.

## M9.1 — Chat read-only

Entregue:

- `dcx chat` no projeto atual, com `--workspace`, `--session` e `--list`.
- Sessão persistente em `.dcx/sessions/<session_id>/session.json`, com `mode: "explore"`, provider, modelo, mensagens e custo por resposta.
- Streaming da resposta do Claude via `--output-format stream-json` e `--include-partial-messages`.
- Claude em `--permission-mode plan`, com `Read`, `Glob` e `Grep`; `Bash`, `Edit`, `Write` e `NotebookEdit` são negados.
- Histórico limitado às 40 mensagens mais recentes e a 48 mil caracteres; mensagens individuais são truncadas em 12 mil caracteres.
- Comandos de sessão: `/help`, `/session` e `/exit`.
- Carregamento de `.env` do projeto/workspace, com `DCX_ENV_FILE` explícito; a `ANTHROPIC_API_KEY` do arquivo é aplicada diretamente ao Claude, e `.env` não é copiado para runs.
- Testes de integração com Claude falso cobrindo streaming, persistência, retomada, listagem e ausência de escrita no projeto.

Não faz parte do M9.1:

- Escrita no projeto, contrato, sensores ou execução.
- API local, interface desktop ou múltiplos clientes.
- Streaming de ferramentas ou eventos intermediários na interface.

## Aceite

- Uma conversa de dois turnos mantém o histórico e a segunda chamada inclui a primeira resposta.
- O projeto permanece inalterado; apenas `.dcx/sessions` é escrito.
- A sessão pode ser retomada pelo id e aparece em `dcx chat --list`.
- O provider recebe modo `plan` e não recebe permissão de escrita ou `Bash`.

## M9.2 — Daemon local

Entregue:

- `dcx serve --bind HOST:PORT` abre um daemon HTTP local.
- `GET /health` responde um estado mínimo para o cliente verificar disponibilidade.
- `GET /sessions` fornece a rota inicial do catálogo de sessões.
- `POST /chat` recebe `workspace`, `session_id` opcional e `message` em JSON.
- A resposta de `/chat` usa SSE e publica `session`, `token`, `done` ou `error`.
- O daemon reutiliza persistência e provider do `dcx chat`; não cria um segundo formato de sessão.

Limites atuais:

- O daemon é local e não possui autenticação ou exposição remota.
- `/sessions` ainda é um endpoint de compatibilidade; o catálogo por workspace entra no próximo ajuste.
- Não há escrita no projeto nem início de run pela API.
