# M2 — Sensores robustos

## Objetivo

Implementar os sensores de aceite antes do código, travá-los contra alteração e usá-los para reprovar atalhos que só passam nos testes visíveis.

## Escopo

- `acceptance_author` escreve os sensores a partir do contrato aprovado, antes da implementação.
- Proporção de sensores ocultos concentrada nos critérios com atalho tentador; pelo menos um por contrato.
- Checksum da suíte e de cada sensor, conferido antes de cada rodada.
- `check_sensors_fail` roda os sensores contra o baseline e recusa sensor que já passa sem implementação.
- `sensor_dispute`: o executor contesta, o humano decide; uma contestação aceita reescreve apenas o sensor contestado e renova o checksum.
- `verdict.issues` saneados antes de voltar ao executor.
- Rodadas de verificação limitadas.
- Plano com vários passos em `job-02`, cujo atalho de comparação exata precisa ser reprovado pelo verifier.

## Entregue nesta fatia

- `SensorLock` e `sensor_lock.schema.json` com checksum SHA-256 da suíte e de cada sensor.
- `SensorLock::verify` recusa conteúdo alterado, sensor adicionado ou removido.
- `check_sensors_fail` trata sensor que não executa como falha esperada do baseline e bloqueia sensor que já passa.
- O demo e o piloto travam a suíte e executam a checagem em um workspace vazio antes de chamar o executor.
- Limite separado de rodadas de verificação (`RunCoordinator::with_verification_limit`).
- Issues geradas pela engine para falha oculta não expõem o id, os inputs nem o texto do sensor.
- `sensor_implementation` e `sensor_implementation.schema.json`: um script Python por sensor, validado contra a suíte.
- `harness-sensors`: materializa os scripts fora do workspace, deixa-os somente leitura e recusa execução se o arquivo não corresponder ao source travado.
- Cada script recebe `HARNESS_WORKSPACE`, `HARNESS_SENSOR_ID` e `HARNESS_CRITERION_ID`; exit 0 aprova, outro código reprova, e o runner aplica timeout de 60 s.
- O demo e o piloto passam a usar sensores Python executáveis em vez do runner fixo em Rust.

## Pendente

- Papel `acceptance_author` que gera `sensor_implementation` a partir do contrato aprovado.
- Diretório de sensores persistente e fora do worktree do executor; hoje ele fica em temporário.
- Sandbox de sistema operacional para os scripts; hoje eles rodam com o usuário atual.
- Contestação de sensor e reautoria parcial.
- Saneamento das issues produzidas pelo próprio verifier.
- Plano multi-passo de `job-02`.

## Validação

- `cargo test --workspace` cobre a detecção de adulteração da suíte e a recusa de sensores que já passam.
- `harness run --demo` imprime o checksum travado e confirma que os três sensores Python falham no baseline antes da implementação.
- `crates/harness-sensors` cobre aprovação, reprovação com stderr, timeout e script adulterado.
